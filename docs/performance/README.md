# Измерение затрат SDL-рендерера

Оптимизация сохраняет разрешение и качество изображения. `TSDLDevice` повторно
использует буфер вершин и индексы triangle fan. Triangle list передаётся SDL без
избыточного массива последовательных индексов. Хранилища текущей текстуры и
render target определяются при привязке, вместо `QueryInterface` на каждом draw.
Интерфейсы сохраняют владение ресурсами; после device reset и смены target
буферы остаются пригодны, а указатель target обновляется.

Измерения выполняются под QEMU с SDL dummy/software. Они показывают затраты
пути отрисовки на CPU облачной машины, а не FPS реальной приставки. Основная
сборка использует SDL с ускорением и прежним автоматическим fallback; частота
кадров на устройствах зависит также от GPU, драйвера, разрешения панели,
масштабирования, VSync и сложности сцены.

`tools/tests/render_throughput.pas` рисует по 2048 объектов: интерфейс с масштабом
800/1024, спрайты при 1024×768, смесь fans/lists/линий/точек/wireframe с ростом
буферов, затем интерфейс после device reset. Каждый замер включает SDL flush,
чтобы учитывать выполненную отрисовку. ReadPixels и подсчёт хеша исключены из
замеряемого времени. Все контрольные суммы кадра до и после должны совпасть
на каждой архитектуре. Между архитектурами побитное совпадение не требуется.

Для повторения соберите fixture с теми же FPC-флагами, что и игру, в отдельных
каталогах units/output для исходной и оптимизированной версии. Сохраните
исполняемые файлы и отдельную неизменяемую копию библиотек. Во время проверки
нельзя заменять библиотеки или бинарники, которые использует QEMU.

Сравнение готовых fixture:

```sh
python3 tools/tests/render_compare.py \
  --arch armhf \
  --baseline /path/to/baseline/render_throughput \
  --optimized /path/to/optimized/render_throughput \
  --library-dir /path/to/immutable-libraries/armhf \
  --sdk-root /workspace/.cloud-setup/anbernic \
  --qemu /workspace/.cloud-setup/sysroot/usr/bin/qemu-arm \
  --output /tmp/render-armhf.json
```

Для AArch64 замените архитектуру на `aarch64`, пути к библиотекам/fixture и
QEMU на `qemu-aarch64`. Скрипт закрепляет процесс за одним доступным CPU и
сравнивает версии в порядке исходная → новая → новая → исходная. В каждом
запуске берётся медиана семи замеров, затем медиана двух запусков версии.
Проверяются хеши кадров и неизменность исполняемых файлов. Измеряйте без
параллельных сборок и игровых тестов.

## Второй этап: настройки текстур

Сборка v2 хранит режимы фильтрации и смешивания в `TSDLStorage`. При создании
нового SDL handle оба значения сбрасываются в неизвестное состояние. Копирование
поверхностей, readback и показ screen texture обновляют тот же кеш; временные
upload/gamma textures сохраняют прежний путь. Изменение фильтрации по-прежнему
завершает уже поставленные в очередь операции перед сменой режима.

`tools/tests/texture_state.pas` проверяет восстановление линейной фильтрации
и прозрачности после nearest-копирования, Present, device reset и пересоздания
ресурсов. Кадр с полупрозрачной красно-зелёной текстурой поверх синего фона должен
сохранять тот же хеш. Отрицательный контроль с пропущенным обновлением кеша при
копировании выявляет потерю синего канала. Оба штатных теста проходят на ARMHF
и AArch64. Минимальное разрешение и качество изображения сохраняются.

## Третий этап: FPS в космосе и расчёт интервала кадров

Исходная версия — `914ae58`. В новой версии границы отсечения кешируются вместе
с масштабом и смещением; draw использует уже вычисленное преобразование. Кеш
хранит результат расчёта координат, поэтому смена SDL target, копирование
поверхностей и readback продолжают устанавливать фактическое состояние SDL.

Ограничитель показа использует точный счётчик SDL и сохраняет дробную часть
интервала. Обычная задержка планировщика больше не начинает каждый интервал
заново. После пропуска целого интервала следующий дедлайн отсчитывается от
текущего времени, чтобы исключить серию догоняющих показов. VSync и браузер
сохраняют своё управление показом. Цикл также пропускает дополнительный
`Sleep(1)` при отключённом лимите и когда отрисовка уже заняла бюджет кадра.
Быстрые кадры с лимитом сохраняют паузу для передачи управления другим потокам.
Игровые таймеры по-прежнему получают фактически прошедшее время.

[Полный отчёт](space-fps-results.json) содержит исходные прогоны, хеши бинарников,
исходников и кадров. Замеры игры: одна начальная кампания из одного autosave,
800×600, SDL dummy/software, VSync выключен, один CPU облачной машины,
порядок исходная → новая → новая → исходная. Каждый прогон измеряет 20 секунд
в космосе; таблица показывает медиану двух средних FPS каждой версии.
Профилирующая библиотека перехватывает SDL Present и geometry в обеих версиях.

| Игровой сценарий | Было → стало, FPS | Изменение |
| --- | --- | --- |
| x86_64, лимит отключён | 205,42 → 267,77 | +30,35% |
| x86_64, лимит включён | 35,57 → 43,49 | +22,25% |
| x86_64, лимит включён, искусственная пауза 25 мс перед Present | 33,08 → 34,15 | +3,24% |
| ARMHF под QEMU, лимит включён | 41,88 → 44,03 | +5,13% |
| AArch64 под QEMU, лимит включён | 46,57 → 53,96 | +15,87% |

В AArch64-процессе отдельно проверены настройки ограничителя: 60 Гц,
`DisableFrameLimit=False`, частота счётчика SDL — 1 ГГц. Разброс исходной
AArch64-версии заметен: 44,35–48,80 FPS; новой — 53,96–53,97 FPS.
Эти данные показывают результат конкретного облачного сценария. Они не
подтверждают FPS приставок, работу аппаратного ускорения или результат в
поздней кампании и бою. Скорости разных архитектур нельзя сравнивать напрямую.

Отдельный `render_throughput` подтверждает сокращение времени спрайтов на
5,26% для ARMHF и 4,84% для AArch64. Для интерфейса 800×600 — 11,87% и 6,02%.
Хеши кадров совпали до и после на каждой архитектуре. Смешанный сценарий на
AArch64 оказался медленнее на 0,72%, при перекрывающихся диапазонах замеров;
равномерного выигрыша во всех примитивах нет.

`tools/tests/frame_pacing.pas` проверяет 50/60/120 Гц, точный дедлайн,
дробные интервалы, задержки, восстановление после паузы, смену частоты и reset.
`tools/tests/clip_transform.pas` проверяет каждый пиксель отсечения при смене
масштаба и смещения камеры, render target, scissor и пересоздании устройства.
Оба теста проходят на x86_64, ARMHF и AArch64; проверки текстур и щелей также
проходят на обеих ARM-архитектурах. Финальные игровые сборки загружают кампанию,
открывают ангар и выходят в космос при 800×600. Нативная сборка дополнительно
прошла создание новой кампании и переход через станцию.

Для повторения в подготовленной облачной среде активируйте
`/workspace/.srhd-env/activate.sh`. Инструкции сборки и запуска тестов сохранены
в настройках среды. Измеренные renderer-fixture сохранены в
`.local/performance/recorded-fixtures/`, игровые результаты — в
`.local/performance/`. ARM sysroot на Debian 13 и полученные с ним бинарники
предназначены для QEMU-проверок. Для выпуска на приставках нужен совместимый
с прошивкой SDK из инструкции BUILDING.md; пакеты для прошивок на этом этапе
не создавались.

### Сборка для выпуска 2026-10-12

В следующей сборке резервный лимит изменён с 50 на 60 FPS. Он применяется
только когда частоту видеорежима и экрана определить не удалось. Настройки
`DisableFrameLimit` и `VSync` сохраняют прежнее действие. Замеры выше относятся
к версии до изменения резервного значения; проверенный ARM-сценарий использовал
определённые 60 Гц и не зависел от этого значения.

Для пакетов Anbernic выполняется отдельная сборка с Ubuntu 20.04 sysroot.
Совместимость ELF и запуск итоговых пакетных бинарников проверяются отдельно;
данные и контрольные суммы этого выпуска приложены к релизу. Замеры на Debian 13
не следует переносить на эту сборку как измерение её FPS.

## Четвёртый этап: вывод полного кадра и ожидание срока показа

Сравнение выполняется с опубликованным билдом `anbernic-space-fps-2026.10.12`
(исходники `628ca3a`). Оригинальные ELF сохранены отдельно перед изменениями.

Если изображение закрывает всё окно, непрозрачный `RenderCopy` заменяет каждый
пиксель. Предварительная очистка окна в этом случае удалена. При несовпадении
пропорций очистка сохраняется: горизонтальные и вертикальные полосы остаются
чёрными. Обе ветки — desktop logical size и native raster — проверены отдельно,
включая изменение размера, гамму и пересоздание устройства.

Программный ограничитель теперь ждёт ближайший срок показа готового кадра.
`Sleep(0)` уступает CPU без запроса задержки в 1 мс. Раньше ранний кадр мог
остаться непоказанным, после чего игра снова выполняла отрисовку. В облачном
x86_64-сценарии это приводило к примерно 177–180 тысячам вызовов geometry за
20 секунд; итоговая версия выполняет 48–49 тысяч и показывает больше кадров.
VSync и браузер используют прежний отдельный путь. Резервные 60 FPS и параметры
`DisableFrameLimit`/`VSync` сохранены. Игровые таймеры получают фактически
прошедшее время, включая ожидание срока показа.

На каждой архитектуре выполнены четыре прогона: исходная → новая → новая →

## Пятый этап: непрозрачные текстуры RGB565

База сравнения — четвёртый этап, коммит `14cd33f`. Его исполняемые файлы и
библиотеки сохранены отдельно до следующего изменения renderer.

Для обычной текстуры RGB565 без alpha-канала и геометрии, у которой alpha всех
вершин равна 255, теперь используется `SDL_BLENDMODE_NONE`. Это позволяет SDL
заменять пиксели без смешивания с предыдущим содержимым. При полупрозрачной
вершине или другом формате восстанавливается `SDL_BLENDMODE_BLEND`. Render
target исключён из быстрого пути: его backing texture имеет формат ARGB,
даже если запрошен RGB565. Фильтрация и модуляция цвета сохраняются.

`tools/tests/opaque_texture.pas` проверяет восемь комбинаций point/linear
фильтрации, полной и частичной непрозрачности, оттенка и различной alpha
вершин. Каждый вариант повторяется после reset и копирования через `StretchRect`;
дополнительно проверяется
смешивание при отрисовке в RGB565 render target. Хеши всех восьми вариантов
должны совпадать между базовой и новой версией на своей архитектуре.
Архитектуры могут различаться побитно при линейной фильтрации.

При запуске fixture с `--bench` дополнительно измеряется синтетический цикл
очистки, отрисовки одной RGB565-текстуры на весь экран 800×600 и вывода кадра:
семь замеров по сто кадров после десяти кадров прогрева. Эта величина не
заменяет измерение FPS в игре.

## Шестой этап: заливка непрозрачных прямоугольников

База сравнения — пятый этап, коммит `7bc72e8`. Его итоговые исполняемые файлы
и библиотеки сохранены отдельно перед изменениями.

`DrawColoredRect` теперь передаёт две треугольные грани вместо четырёх.
Раньше две дополнительные грани имели нулевую площадь; для их формирования
также читалась лишняя вершина. Контрольные суммы стандартного прямоугольника
и прежнего замкнутого fan совпали во всех проверенных конфигурациях.

SDL-адаптер выводит одноцветный непрозрачный прямоугольник без текстуры через
`SDL_RenderFillRect` с `SDL_BLENDMODE_NONE`. Быстрый путь применяется только
к четырём вершинам triangle fan, с целыми физическими координатами, одинаковым
цветом и alpha 255, положительными шириной и высотой. Scissor уже преобразован
в координаты target. Дробные края, оттенки по вершинам, прозрачность,
повёрнутые и скошенные фигуры, wireframe и другие fans сохраняют прежнюю
отрисовку треугольников. Следующий draw восстанавливает нужный режим смешивания.

Новая проверка `tools/tests/solid_rectangle.pas` сравнивает 27 вариантов:
девять форм/режимов при трёх масштабах и смещениях. Каждый вариант рисуется
с обрезкой поверх полупрозрачного target и повторяется после reset. В том числе
проверены стандартный и прежний замкнутый fan, частичная непрозрачность,
разные цвета вершин, дробные края, skew, дополнительные недегенеративные
треугольники, wireframe и обратное направление вершин.

`opaque_texture.pas` дополнительно поддерживает `--rgba` и `--rgbx`.
Проверяются изменения alpha последнего texel после загрузки, включая
пересоздание managed handle. RGBX намеренно содержит нулевой неиспользуемый
байт alpha. Сравнения сохраняют исходные пиксели всех трёх форматов текстур.

На x86_64, ARMHF и AArch64 прошли 48 запусков fixture: новый тест,
`opaque_texture` в трёх форматах, `presentation_coverage`, `texture_state`,
`ui_tile_seams` и `clip_transform` для исходной и новой версии. Ещё 16 запусков
нового теста и трёх форматов текстур прошли через native SDL OpenGL и OpenGL ES 2
с Mesa offscreen. Все сравниваемые хеши пикселей совпали на своём renderer
и архитектуре. Это функциональная проверка API, а не аппаратного FPS.

## Седьмой этап: очередь SDL и пакет непрозрачных точек

База сравнения — коммит `c1b4a8e`, после удаления лишних граней прямоугольников.

Приложение задаёт `SDL_RENDER_BATCHING=1` через SDL hint. В SDL 2.32.4 явное
имя драйвера в `SDL_RENDER_DRIVER` иначе отключает очередь команд. Рендерер
игры использует SDL API; SDL копирует переданные вершины до возврата из draw,
а смена target, чтение пикселей и изменение используемых текстур выполняют
нужный flush. Переменная окружения `SDL_RENDER_BATCHING=0` сохраняет приоритет
над обычным hint и остаётся явным пользовательским переопределением.

На ускоренном renderer масштабированные непрозрачные точки отправляются
одним `SDL_RenderGeometry`. Для каждого пиксельного блока используются прежние
целочисленные границы и два треугольника; порядок точек и их цвета сохранены.
CPU-буфер вершин растёт по мере необходимости и переиспользуется между кадрами
и reset. Программный renderer, масштаб 1×1 и пакет с хотя бы одной
полупрозрачной вершиной используют прежний путь. Признак ускорения читается
при reset устройства, без запросов renderer info на каждой точке.

`point_blocks.pas` проверяет шесть масштабов/смещений, включая 0,625 и 0,78125,
и пять размеров пакета: 8, 127, 512, 16 и 0 точек. Повторяющиеся координаты
проверяют порядок перекрывающихся точек; смешанная alpha проверяет резервный
путь. Проверены отрицательные и дробные координаты, scissor, привязанная
текстура, рост и повторное использование буфера, reset. Цветовые
компоненты не округляются дополнительно: в SDL передаются исходные RGBA bytes.

`force_accelerated_info.c` — только тестовый preload. Он изменяет публичную
копию флага renderer, чтобы выполнить новый путь на ARM/QEMU с SDL software.
Сам SDL backend остаётся программным. Эта проверка проверяет генерацию
геометрии и пиксели ARM-кода, а не физический GPU.

### Игровой FPS итоговых ELF через OpenGL ES 2

Два отдельных сценария выполнены в порядке исходная → новая → новая →
исходная, по 20 секунд космоса из одного автосохранения. Native x86_64,
Mesa offscreen, один CPU, VSync и лимит FPS выключены. Каждый прогон проходит
ангар и вылет; текущий renderer проверен по журналу как `opengles2`.

| Сценарий | Было → стало, FPS | Изменение | Диапазоны исходной / новой версии |
| --- | --- | --- | --- |
| 1024×768, явный GL-драйвер без env override очереди | 90,97 → 94,05 | +3,40% | 90,77–91,16 / 93,67–94,43 |
| Логическое 1024×768 → выход 640×480, очередь включена обеим версиям | 239,67 → 244,47 | +2,00% | 239,29–240,05 / 243,28–245,66 |

В первом сценарии очередь исходной версии отключалась из-за явного имени
драйвера, а итоговая версия включает её через hint. Масштаб равен 1, поэтому
пакетный путь точек не применяется. Во втором сценарии тестовый preload
фиксирует физическое окно 640×480, сохраняя логический framebuffer 1024×768.
`SDL_RENDER_BATCHING=1` задан обеим версиям, `LP_NUM_THREADS=1`; сценарий
проверяет дополнительный эффект пакета точек при уже включённой очереди.
Сравнивать строки таблицы между собой как эффект одного изменения нельзя.

Время внутри `RenderGeometry` в первом сценарии падает примерно с 5,07 до
0,03 мс/кадр, но это перенос исполнения команд к flush, а не такое же
сокращение полного кадра. Основной результат — общий игровой FPS выше.
Все восемь игровых прогонов завершились с кодом 0 и актуальным снимком космоса.
Нативный GL-путь Mesa проверен; аппаратный FPS приставок не измерялся.

Цикл включает очистку, 512 непрозрачных точек и прямой вывод при 128×96.

## Восьмой этап: повторная загрузка GI-кадров космических объектов

База сравнения — `875e743`. В `TSpaceImgGI.Draw` готовая текстура теперь
используется без предварительного `LoadFrameGi`. Индекс кадра в последовательности
вычисляется один раз вместо четырёх, а текстура запрашивается один раз вместо
двух. Создание отсутствующей текстуры по-прежнему загружает и декодирует GI.
Смещение читается после создания текстуры; порядок объектов и scissor сохранены.
Программный путь через `ScreenRenderBuffer` сохраняет загрузку кадра.

`space_image_cache.pas` создаёт GAI с обычным и сжатым LZ/zlib RGB565-кадрами,
переставленной последовательностью, ненулевыми координатами и пустым кадром.
Девять случаев проверяют объекты и фон, полное и частичное отсечение, невидимые
тайлы. Каждый выполняется при первом выводе, повторном выводе, очистке кэша
текстур и reset. Тест очищает `DecodedFrameGi`: исходная версия снова загружает
GI, новая при готовой текстуре оставляет его пустым. Опция `--baseline`
проверяет поведение исходной версии. Для фона проверяется прежняя загрузка GI.

Десять запусков проверки: обе версии на трёх архитектурах через SDL software,
затем обе версии через native OpenGL и OpenGL ES 2. Все сравниваемые пиксели
совпали. ARMHF и AArch64 собраны с прежними библиотеками; используются
неизменяемые ELF варианта с изменением только `GI_SpaceImg.pas`.
